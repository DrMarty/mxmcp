# Open Source Notes: Repository Structure, Release Process and Compliance Boundaries

## 1. What This Repository Is / Is Not

**It is**: an independently implemented MCP server (`mxmcp`) that either
① drives a local installation through STM32CubeMX's **official command line** (hybrid mode), or
② works fully offline using a bundled data pack (standalone mode).

**It is not**: a repackaging or cracked version of CubeMX, or any redistribution of ST content. The repository contains no
ST binaries, firmware packages, templates or database files — these are generated locally **by users from their own legally installed
CubeMX** (`python -m mxmcp.bundle build`).

## 3. Release Process

```bash
# 1) Validate source code
ruff check .
python -m mxmcp.server --selftest
pytest tests -q

# 2) Compliance check (must pass)
python tools/check_compliance.py

# 3) Build distributables
python -m build          # dist/mxmcp-<ver>.tar.gz + .whl (contains no ST data)

# 4) Tag
git tag v1.1.0 && git push --tags
```

CI (`.github/workflows/ci.yml`) runs lint, protocol self-test, unit tests and the compliance check on Ubuntu/Windows × py3.9/3.11/3.12,
and asserts that the wheel contains no ST-derived files.

## 4. Required Reading for Users: Build the Data Pack After Installing

Standalone mode requires the data pack:

```bash
python -m mxmcp.bundle build --cubemx-root "/path/to/STM32CubeMX"
python -m mxmcp.bundle verify
python -m mxmcp.server --selftest
```

Without CubeMX installed, only the **pure-code paths** are available (protocol, tool signatures, `.ioc` read/write,
project model); MCU selection/pins/generation will return an explicit message. This is a deliberate design: the data must be
generated by users from their own installation.

## 5. Reverse-Engineering Boundaries (What We Did and Did Not Do)

What we did (all locally, against our own installation):

* Static: embedded archive structure analysis, `javap` class/method/field listings, constant-pool string and endpoint scanning,
  XSD/XML data model, `.ioc` and template corpus statistics, PE certificate/import table/resource table.
* Dynamic: `-i`/`-q` interactive protocol, empirically tested semantics of 267 commands, classification of hang scenarios.
* Artifacts: the data pack and `analysis/*.json`, for local interoperability and documentation.

What we did not do, and do not provide:

* Bypassing/cracking any license or login check (`login`/`swmgr` only invoke the official commands).
* Distributing ST binaries, firmware packages, templates or databases.
* Modifying the CubeMX installation or the registry.
